## 3. I7 — silent error handlers

There are 189 handlers whose whole body is `pass` / `continue` / `return None`; 8 are
bare `except:`. By folder: Observatum 108 (45 of them in the import wizards), DataEntry 28
(none in commit/write), scripts 24, Examen 12, shared 6, Atrium/Curator/Lector 3 each,
Codex/Munia 1 each. The full list is `scratchpad/tools/silent.txt` (this session).

**High — can lose or duplicate records (F35):**
1. `observation_import_wizard/validation_worker.py:909, :924`: the iRecord-sync duplicate lookups (`… IN (…)`, unbatched) are wrapped in `except: pass`. If either fails, nothing is marked duplicate. Then `irecord_id UNIQUE` makes `executemany` fail, `_batch_insert_observations` prints and returns 0, and **the whole 500-row batch is lost, new records included**.
2. `scheme_import_wizard/validation_worker.py:1015, :1039`: same pattern. `nbn_atlas_id` has no UNIQUE, so a failed lookup **re-imports the whole NBN file as duplicates**.
3. `specimen_import_wizard/validation_worker.py:421`: a sort-key lookup failure leaves `taxonomic_sort_key` NULL. The specimen is then **invisible in the collection sidebar**, the same failure as the 244 lost specimens.

**Medium:**
- Personal duplicate check `:967` is swallowed, so "skip duplicates" silently does nothing.
- Species-lookup exceptions are reported as "Species not found". In iRecord-sync mode that is only a warning, so the record is imported without a TVK.
- Taxonomy enrichment: a single failure drops the sort key and superfamily for a whole 500-TVK batch.
- Lat/long derivation failure: the record is imported with no coordinates and no warning.
- Quantities like "c.20" or "5+" become 1. An unparseable `irecord_id` becomes None, which loses the dedupe key.
- `wizard_import_mixin.py:571`: a DB error restarts the `observatum_key` sequence at 0001. Imports use 4-digit sequences but the model uses 6-digit, and "last key" is found by a string sort.
- `scheme_import_wizard/wizard_file_mixin.py:234`: `utf-8` is tried before `utf-8-sig`. For a BOM-prefixed iRecord CSV, the first header becomes `﻿ID`, so **every irecord_id is lost**.

All three wizards share one batch behaviour: if a single row fails in `executemany`,
the whole batch is counted as errors and none of it is written. It is printed to the
console, not shown to you.

**How much of this has actually happened** can be checked read-only:
- records with a NULL `taxonomic_sort_key` by import batch;
- recording_scheme rows with NULL `irecord_id` from iRecord files;
- duplicate `nbn_atlas_id`s;
- duplicate `observatum_key`s.

That check is the next step before any repair (backlog I7b).
